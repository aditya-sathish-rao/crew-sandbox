What shape should the host authority take?

One process holds the model key, another holds the GitHub App key. Step 6 of the migration plan asked whether they should be a system daemon, a user agent, or something the CLI starts on demand. A user agent already ships. This page is the evidence for whether that was the right call — and where the answer should be split.

The premise is narrower than the doc claims. The measurement that justified the user agent ran a job in gui/$(id -u), not in system/. It proves a TTY-less user-domain job can read the vault once someone approves. It does not test a root LaunchDaemon. See the evidence gap.

The axis that decides it is lifetime, not privilege

All three shapes can read the key. They differ in when the process exists relative to login, and therefore in who is available to answer the vault.

The three options, costed

1 · The gateway fails quiet, the broker fails loud

If the vault returns nothing, the broker refuses to start — it exits with status 2 and the log says why. The proxy does the opposite: it prints one line and runs on without a model gateway, still serving egress. A daemon that loses the key at boot therefore produces the worst pair — a boundary that reports healthy while the model is off.

internal/broker/broker.mjs:22-27 · internal/proxy/proxy.mjs:47,235 · cmd/crew-sandbox/main.go:399

2 · Revocation is custody of a process, not of a host

A minted token is remembered only in the broker's in-memory map. Restarting the broker strands every token it issued — which is a safe failure, until crew-sandbox down is the thing that needs to revoke. It calls the running broker and says "no token broker is running; no tokens to revoke" when there is none. An on-demand broker that exits between requests therefore breaks the one lifecycle guarantee the security model leans on.

The evidence gap worth closing in this task

The doc's conclusion is sound, but it is one inference longer than its evidence.

what was run

A job bootstrapped into gui/$(id -u) with RunAtLoad, ppid 1, no TTY. Several secrets, including a multiline PEM.

Every plain inject returned the value and was recorded approvalSource: Manual, "Approved in prompt".

what it supports

"A user-domain job with no terminal can read the vault, once a human approves." That is exactly enough for B — and it is the part of the claim the shipped module depends on.

It does not establish that a root daemon in system/ fails: different domain, different user, different vault. One run there closes the question either way.

Suggested edit: in docs/darwin-module.md:50-53, change "a LaunchDaemon would … simply fail" from an assertion to the narrower, provable statement — that a daemon cannot obtain the key without an operator-arranged policy. Then either run the system/ probe or cite the policy gap as the reason the option is out.

Recommendation: split the question by lifetime

The three options are not three answers to one question. The proxy and the broker have different reasons to stay up, and those reasons point the same way.

keep Proxy → user LaunchAgent (unchanged)

It must be up for the guest's entire life, and the guest is login-bound anyway. Keeping it as an agent means the key read always has a desktop to land on, and the failure direction stays closed.

keep Broker → user LaunchAgent, not on demand

Not because of privilege but because of custody: its memory-only token map is what down revokes against. A process per task cannot hold that map across tasks.

narrow On demand → the right shape for gates and one-off runs

Which is what verify/gates/check.sh already does: start by port if free, reap by port on exit. That pattern is correct there and should stay there.

the real lever Endorse the wrapper, not the domain

What would make a boot-time read possible is not root — it is policy: av bless --endorse-launcher against the wrapper nix already generates, or a Temporary Access Grant bound to it. That choice belongs to the operator, and it is the only thing that turns "daemon" from unchosen into choosable.
